# Authentication

ClinikAPI uses API key authentication via the `x-api-key` header. Every request must include a valid key.

## API Keys

Keys are created in the [Developer Dashboard](https://dashboard.clinikapi.com) (see [Access: API keys](/dashboard/projects/access-keys) for the screen) and follow this format:

| Format | Environment | Use Case |
|--------|-------------|----------|
| `clk_test_*` | Test | Development, staging, CI/CD |
| `clk_live_*` | Production | Live patient data (paid plans; not available yet, see below) |

```bash
curl -X GET https://api.clinikapi.com/v1/patients \
  -H "x-api-key: clk_test_abc123def456"
```

```ts
import { Clinik } from '@clinikapi/sdk';

const clinik = new Clinik(process.env.CLINIKAPI_SECRET_KEY!);
```

## ClinikAPI is a Data API

ClinikAPI does **not** handle end-user authentication. You bring your own auth provider (Clerk, Auth0, Firebase, etc.) and use ClinikAPI purely for clinical data storage and retrieval.

```
Patient (browser) → Your Auth (Clerk/Auth0) → Your Backend → ClinikAPI SDK → ClinikAPI
```

The SDK runs on your server. Your backend authenticates the end user, then calls ClinikAPI with your secret key.

## Tenant Isolation

Every resource stored in ClinikAPI is tagged with your organization's tenant ID:

```json
{
  "meta": {
    "tag": [
      {
        "system": "https://clinikapi.com/tenant",
        "code": "org_abc123"
      }
    ]
  }
}
```

- **On create**: the tenant tag is automatically injected
- **On search**: a `_tag` filter is automatically applied — you can only see your own data
- **On read/update/delete**: ownership is verified before the operation proceeds

There is no way to access another tenant's data through the API.

## Multi-Datastore Routing

Requests are routed to different datastores based on your key and plan:

| Key Type | Plan | Datastore |
|----------|------|-----------|
| `clk_test_*` | Any | Shared test datastore |
| `clk_live_*` | Pro | Isolated data store on our shared production infrastructure (Small) |
| `clk_live_*` | Team | Dedicated server (Medium), with a failover standby |
| `clk_live_*` | Enterprise | Private architecture: a private network or your own cloud account |

Dedicated servers start at the Medium size. A Pro project can upgrade to Medium or larger, and moving keeps every record and id, while earlier version history stays with the old copy. Free and Pro data is stored in the United States. Team and Enterprise can choose another region; regions open on request. Enterprise customers get a fully isolated datastore provisioned in their chosen region. Live data is not available yet.

<Note>
Live data isn't available yet. Requests with a live key return `503` (`LIVE_STORE_UNAVAILABLE`) until live storage is switched on for your project. Use a test key meanwhile. The same API address, `https://api.clinikapi.com/v1`, serves both; the key decides which environment a request reaches.
</Note>

## Key Validation Flow

For minimal latency, API keys are validated against a co-located PostgreSQL database that mirrors your dashboard data:

1. You create/revoke keys in the Dashboard
2. Key changes are automatically synced to the co-located database
3. The API validates keys locally — no cross-region round trips

Keys are cached for 60 seconds to minimize database lookups.

## Keys and Projects

A key belongs to one project. The project is the data boundary: a test key reads and writes only its own project's sandbox data. If the project's billing has stopped the key is refused with `402 PAYMENT_REQUIRED`; if it is paused, `503 PROJECT_PAUSED`; while it is being set up or resized, `503 PROJECT_NOT_READY`. Refused requests are not counted against your quota or rate limit. See [Errors](/errors#project-status).

## Key Scopes

Every API key carries scopes, and the API checks them on each request:

- `read` — GET operations
- `write` — POST, PATCH and DELETE operations

Keys created in the Dashboard carry both `read` and `write`. A request outside a key's scopes is refused with
`403` and the error code `INSUFFICIENT_SCOPE`. A key with no scopes at all is refused.

Live keys (`clk_live_`) can be created only by an organization owner or admin, and only on a paid plan. Test keys
(`clk_test_`) are available on every plan. A key's secret is shown once, when you create it; see [Access: API keys](/dashboard/projects/access-keys).

## Security Best Practices

<Warning>
  Never expose your API key in client-side code, Git repositories, or logs.
</Warning>

- Store keys in environment variables (`CLINIKAPI_SECRET_KEY`)
- Use `clk_test_*` keys for development — they route to an isolated test datastore
- Rotate keys periodically from the Dashboard
- Use scoped keys when possible (e.g., read-only for analytics services)
- For client-side UI, use `@clinikapi/react` with the [proxy pattern](/components/overview)
